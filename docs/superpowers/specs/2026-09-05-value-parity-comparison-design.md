# 값 병행 비교 (Value Parity) — 두 서버 응답의 값 동등성 검증과 노이즈 제거

**Date:** 2026-09-05 · **Status:** design for review · **Builds on:** the shipped matrix-job +
env-comparison report (`docs/superpowers/specs/2026-09-04-multi-dimension-jobs-design.md`), and the
validation-rules / format-library propose→approve pattern.

## 1. 목적과 지금과의 차이

노후 장비 교체(legacy → renewed) 프로젝트에서, 같은 소스코드가 **새 장비의 서버에서 같은 결과를
내는지**를 대량으로 검증한다. 노후·신규 서버는 endpoint만 다른 두 타깃이라, 이는 dev/stg를 동시에
호출해 비교하는 것과 구조가 같다 — 그리고 그 뼈대는 이미 있다.

**이미 되는 것**: 매트릭스 job이 `api × target × data`를 두 계에 돌리고, 리포트가 계를 열로 놓고
셀을 비교해 다른 행을 표시한다(`reports._matrix`).

**한계(=이 스펙이 채우는 것)**: 지금 비교는 **상태(pass/fail/error)뿐**이다. `RunResult`는 응답
본문을 저장하지 않는다. 그래서 두 서버가 **둘 다 200인데 payload가 다르면 "일치"로 보인다** — 노후/
신규 검증의 핵심(값이 같은가)을 놓친다.

**이 스펙**: 있는 비교 리포트 위에 두 층을 얹는다. (1) **값 동등성** — 응답 본문을 저장하고 필드
단위로 비교, (2) **노이즈 제거** — `serverTime`·`txId`처럼 매번 달라지는 필드를 비교에서 빼서 진짜
차이만 남긴다. 상태-only 비교는 다시 만들지 않는다.

확정된 방향(운영자, 2026-09-05): **실시간 병행 비교**(두 서버 동시 호출), **응답 본문 동등성까지**,
타깃별 인증은 미정이라 기본 동일 + 타깃별 오버라이드 옵션.

## 2. 안전 모델 (변하지 않음)

- 동등성 판정은 **결정론 코드**가 한다(무시 스펙을 적용한 뒤 두 본문을 필드 단위로 비교). 모델은
  "같다/다르다"를 판단하지 않는다.
- 무시 스펙(비교 프로파일)은 **사람이 승인하는 저장 객체**다 — 규칙·포맷과 같은 propose→approve.
- 서버 호출은 **스케줄러**가 하고 LLM이 없다. 리포트도 LLM이 없다(템플릿+data.json).
- 채팅은 오케스트레이션과 자연어 창구, 그리고 무시 스펙 저작만 한다.
- **과거 실행 불변**: 새 비교나 프로파일 승인이 과거 `RunResult`나 그 판정을 바꾸지 않는다.

## 3. 채팅이 실제로 하는 일 (역할 명확화)

무거운 일(호출·저장·비교·판정·리포트)은 전부 결정론이다. 채팅의 값은 두 곳에 몰린다.

- **느슨한 말 → parity job**: "오늘 대상 API 전부 노후·신규에 돌려서 비교" 를 실제 API 집합 + 두
  타깃 + 동일 데이터의 job으로 스테이징(기존 `search_apis`/`select_where` 재사용).
- **무시 스펙 저작(핵심)**: 첫 비교의 차이 클러스터를 보고 "이 필드들은 매번 달라요, 뺄까요?"를
  제안하고, "serverTime·txId 무시해"를 구조화된 프로파일로 번역 → 사람 승인. UI였다면 수백 개
  필드를 사람이 하나씩 체크할 일을, 대화로 걷어낸다.

상태-only 비교만이라면 채팅이 새로 할 게 없다. **값 비교가 생겨야 "이 필드 무시"가 의미를 가진다** —
그래서 이 두 층은 함께 간다.

## 4. 필요한 조각

### 4.1 명명 타깃 (backend/config)

`allowed_target_envs=("dev","stg")` 고정을 **명명 타깃 레지스트리**로 일반화한다: 타깃 =
`{name, endpoint(base_url), (optional) auth/headers}`. parity 실행은 job의 `target_envs`에 두
이름(예: `legacy`, `renewed`)을 넣는다. 인증은 기본 동일, 타깃별 오버라이드는 선택. Mock은 타깃별
엔드포인트를 스텁한다. 리포트는 이미 N개 계를 다루므로 열 수는 문제 없다.

### 4.2 응답 본문 저장 (backend)

`RunResult`에 `response_body: dict | None`(또는 정규화 JSON)을 추가한다. 실제 aTworks에선 캡처한
응답, Mock에선 `stub_response(api, target, data)`가 낸 본문. Mock 스텁은 데모를 위해 (a) 일부
API에서 **타깃 간 결정론적 값 차이**(신규 서버가 한 필드를 다르게)와 (b) **매번 달라지는 변동
필드**(`serverTime`)를 넣어, 값 불일치 + 노이즈 + 클러스터링을 보여줄 수 있게 한다.

### 4.3 동등성 엔진 (host, LLM 없음)

`compare(body_a, body_b, ignore_paths) -> {equal: bool, diff_paths: list[str]}`. JSON 경로 기준
으로 무시 필드를 뺀 뒤 재귀 비교. 순수 함수, 결정론. (숫자 허용오차·배열 순서 무시는 후속.)

### 4.4 비교 프로파일 = 무시 스펙 (승인 객체, 규칙 패턴 재사용)

비교에서 제외할 JSON 경로 목록. 스코프 결정: **parity 실행에 적용되는 프로파일 하나**(그 실행의 모든
API 공통) + 필요하면 **API별 추가 경로**. 이름 붙여 저장·재사용 가능(포맷 라이브러리처럼). 승인은
호스트 전용(규칙 승인 미러). 모델은 경로를 제안만, 사람이 승인.

### 4.5 parity 리포트 (host, LLM 없음)

`_matrix`를 확장한다. 두 타깃 셀에 본문이 있으면, **적용된 무시 스펙**을 걸어 `compare`로 행 판정을
낸다: **일치 / 상태 불일치 / 값 불일치(+diff_paths)**. 상단에 "N개 중 M개 불일치" 집계. 기본은
**불일치만 + 카운트**, 행을 눌러 차이 필드로 드릴다운.

### 4.6 클러스터링 (host)

불일치 행을 **diff_paths 시그니처로 묶는다**: "480개가 `$.serverTime` 하나만 다름", "20개가
`$.balance` 다름". 이게 "대량으로 효과적으로"의 핵심이고, 채팅이 "이 필드 빼면 480개 정리"를 제안하는
근거다.

### 4.7 재비교는 재실행 없이 (핵심 속성)

응답 본문을 저장하므로, **무시 스펙을 바꾸면 저장된 본문을 다시 diff**할 뿐 서버를 다시 부르지
않는다. "serverTime 무시해줘 → 즉시 480개 정리"가 재호출 없이 즉각 이뤄진다. 노이즈 제거 루프가
싸고 빠르다.

## 5. 채팅 워크플로

1. "노후·신규 서버에 오늘 대상 API 다 돌려서 비교해줘" → 대상 해석 + 두 타깃·동일 데이터 확인 →
   **parity job 스테이징** → 승인 → 스케줄러 실행 → parity 리포트.
2. "신규에서 다른 거 뭐야?" → 최신 parity 리포트의 **클러스터 요약 카드**("480개는 serverTime, 진짜
   다른 건 20개").
3. "serverTime·txId 무시해" → 채팅이 **비교 프로파일 초안** 제안 → 승인 → **재실행 없이 재diff** →
   진짜 20개만 남은 리포트. (첫 diff를 보고 채팅이 먼저 제안도 함.)

## 6. MVP 빌드 순서

- **Phase A (엔진, 대부분 우리 쪽)**: 명명 타깃 + 응답 본문 저장(Mock 스텁) + 값 동등성 parity 리포트
  + 클러스터링. 프로파일 승인 흐름 전에도, 리포트가 "이 필드 무시하면 N개 정리"를 즉석 계산해 보여줄
  수 있다.
- **Phase B (승인 객체 + 채팅)**: 비교 프로파일 lifecycle(stage/approve/apply, 재실행 없이 재diff) +
  채팅 저작(제안→승인) + Profiles 화면 + parity 카드.

## 7. 범위 밖 (기록)

- 실제 서버로의 진짜 HTTP 호출 — REST 어댑터의 몫; Mock은 스텁.
- 응답 스키마/레이아웃 비교(필드 구성 변경 감지) — 값 비교와 별개, 후속.
- 숫자 허용오차·배열 순서 무시·정규화 규칙 — 무시 스펙의 확장으로 후속.
- 타깃별 복잡한 인증(OAuth 흐름 등) — 기본 동일 + 단순 오버라이드까지만.
- 기준값(골든셋) 캡처 모드(노후 서버 소멸 대비) — 실시간 병행을 먼저, 후속.

## 8. 테스트/검수 포인트

- 동등성 엔진: 같은 본문 일치, 값 다르면 diff_paths, 무시 경로 적용 후 일치, 중첩/배열 경로.
- 재비교 무재실행: 무시 스펙 적용/변경이 저장 본문을 재diff할 뿐 새 run을 만들지 않음(run 수 불변).
- 클러스터링: 같은 diff 시그니처 묶음, "N개가 이 경로 하나 때문" 카운트.
- 프로파일: 호스트 전용 승인, 채팅이 마크 소비 못 함, 승인이 과거 run 불변.
- 리포트: LLM 없음; 값 불일치/상태 불일치/일치 판정 정확; escape 유지.
- 채팅: parity job 스테이징, 클러스터 요약 카드, 무시 스펙 제안→승인→재diff.
