# Impact matrix: multi-dimension JobSpec (envs × schedules × test data)

Scope: today `JobSpec.target_env: str`, `schedule: JobSchedule | None` (0 or 1), no test
data. Planned change: `target_env` becomes a list, `schedule` becomes a list, and a new
`test_data` (parameter-binding sets) dimension appears, applied identically across every
env — so `stage_job`/`apply_job` expand one job into a matrix of runs
`api_ids × target_envs × schedules × test_data`.

This document is read-only analysis. No code was changed.

## 2. Safety-invariant check (Part C layers)

| Layer | Can the multi-dimension change violate it? | What rule keeps it safe |
|---|---|---|
| **Fixed tool surface** (tool list is a pure function of config, same bytes every turn — `tools/registry.py`, pinned by `test_registry.py: test_same_config_same_bytes`) | Yes, if the new array-typed `target_env`/`schedule` fields or a new `test_data` field are added with anything non-deterministic (e.g., dynamic `maxItems` derived from runtime state instead of config). | Keep the new caps (`max_target_envs_per_job`, `max_schedules_per_job`, a `test_data` count cap, and the overall matrix-size cap) as `AtworksAgentConfig` fields, wired into the schema the same way `max_apis_per_job`/`api_ids.maxItems=500` already loosely are (#13). The existing `test_same_config_same_bytes` test generalizes unchanged as long as this rule holds. |
| **Provenance + guardrails at stage and apply** (`check_api_provenance`, `check_job_guardrails` run twice — stage in `jobs.py:88-91`, apply in `jobs.py:122-129` and mirrored in `gates.py:74-93`) | Yes — this is the layer most directly threatened. Two concrete failure modes: (a) the `allowed_target_envs` check (#6) is naively rewritten as `all(...)` or checks only `draft.target_envs[0]`, letting a `prod` entry anywhere but the first slot slip through; (b) a matrix-size guardrail is added only at `stage_job` and not re-derived at `apply_job` (or vice versa), breaking the documented two-phase intent ("guardrail runs twice — apply time config may have tightened," jobs.py:2). | Every env in the list must be checked with `any(e not in allowed for e in envs)` (not `all`), collecting *all* violating envs into one message the way `check_job_guardrails` already collects multiple violation strings. ## 4. Reference note: `merchant_agent/changes.py` bounding pattern

`refs/commerce-agents/merchant-agent/core/merchant_agent/changes.py:31-108` (`check_guardrails`) is the
existing precedent for bounding a *multi-item* staged write, and maps onto the matrix cap
needed here:

- `StagedChange.items: list[ChangeItem]` (types.py:406 area) already models "one staged
  change can carry many field-level diffs," each with its own `target`/`field`/`before`/`after`
  — structurally the same shape aTworks needs for "one job spans many env×schedule×data
  combinations," except aTworks currently spreads that across three still-scalar fields
  (`target_env`, `schedule`, and the not-yet-existing `test_data`) rather than one list of
  matrix cells.
- `config.max_items_per_change` (merchant config.py:53, default 25) is a **flat count cap**
  on `len(items)` — the direct analogue of aTworks' existing `max_apis_per_job`. It maps
  onto the *new* aTworks cap only if the matrix is flattened into one list of cells before
  staging (one `ChangeItem`-like row per api×env×schedule-occurrence×data combination);
  if instead the four dimensions stay as four separate lists (current direction implied by
  "target_env becomes a list, schedule becomes a list, test_data appears" rather than "one
  flat list of run-cells"), the cap must be a **product cap** (`len(api_ids) × len(envs) ×
  sum(schedule counts) × len(data)`) rather than a flat `len(...)` cap — `changes.py` has no
  existing precedent for a product cap since merchant changes are already flat lists of items.
  This is the one place where naively copying the reference pattern (a flat count) would
  under-guard the aTworks case, because aTworks' dimensions multiply rather than concatenate.
- `changes.py:46-57`'s per-item duplicate-target detection (`if (item.target, field) in seen:
  violations.append(...)`) is the analogue of aTworks' existing `test_stage_job_dedupes_api_ids`
  behavior (executor.py:250 dedupes `api_ids` via `dict.fromkeys`) — the same dedupe-or-reject
  choice needs to be made explicitly for `target_envs` (dedupe silently, like `api_ids` today)
  and for `schedule`/`test_data` entries (where two schedules with identical
  kind/at/tz/from_date/count are likely a mistake worth flagging rather than silently
  deduping, since — unlike api_ids — a repeated schedule is far more likely to be an error
  than an intentional duplicate).
- `changes.py:151-153` and `188-193` (`ChangeLedger.stage`/`apply`) reconfirm the two-phase
  guardrail-recheck pattern (`check_guardrails` called at both stage and apply) that
  `JobLedger.stage`/`apply` (jobs.py:88-91, 122-129) already mirrors — no new pattern needed
  here, just apply the same recheck to the new matrix-size guardrail as it applies to
  everything else already.

## Options where a choice is unavoidable (named, not recommended)

- **"One execution" for multi-schedule jobs**: a single `runs_remaining` counter shared
  across all schedules (simplest, but loses which-schedule-is-due granularity) vs. one
  counter per schedule (correct granularity, larger `JobLedger`/`JobSpec` surface). (#9, #14)
- **Matrix-size cap shape**: flatten envs×schedules×data into one list of cells and reuse
  `merchant_agent`'s flat `max_items_per_change` pattern, vs. keep four separate lists and
  add a product cap. (#8, §4)
- **LATE-binding re-resolution granularity**: resolve `select_where` once per job execution
  (current behavior, extended) vs. once per target env. (#16)
- **Approval scope**: one approval click covers the whole matrix (no approval-layer change,
  but requires the preview card to show the full matrix for informed consent) vs. a
  sub-job/matrix-item approval concept (new surface area, no existing precedent in this
  codebase). (#21, #30, §2)
- **Confidence keying for list-valued slots**: one confidence score per whole field
  (`target_envs`, `schedule`) vs. indexed/nested keys per list item. (#23)
- **Duplicate schedule/env handling**: silently dedupe (like `api_ids` today) vs. reject as
  a likely operator/model error. (§4)
